# Transpose v1：shared-memory tiled transpose

## 1. 优化假设

v0 的读取已经合并，但同一 warp 的 32 个输出分散到 32 个 32-byte sector。
v1 使用 `32×32` shared tile 改变访问顺序：

1. `32×8` 线程块中每线程循环处理 4 个元素，合并读取输入；
2. block 同步；
3. 交换 grid 的 x/y 坐标，经 shared tile 转置后合并写出。

v1 使用 `float tile[32][32]`，暂不 padding。全局事务应恢复合并，但写出阶段
读取 `tile[threadIdx.x][threadIdx.y+offset]` 会让一个 warp 跨 32 行访问相同
bank，预期产生严重 shared-memory bank conflict。

## 3. Sanitizer

以下三类检查均通过：

```bash
compute-sanitizer --tool memcheck --error-exitcode=1 \
  ./build/transpose_v1 --rows=1000 --cols=1023 --warmup=1 --repeat=2
compute-sanitizer --tool synccheck --error-exitcode=1 \
  ./build/transpose_v1 --rows=37 --cols=65 --warmup=1 --repeat=2
compute-sanitizer --tool racecheck --error-exitcode=1 \
  ./build/transpose_v1 --rows=37 --cols=65 --warmup=0 --repeat=1
```

memcheck/synccheck 为 0 errors，racecheck 为 0 hazards，非对齐 tile 的未初始化
位置不会被边界内线程读取。

全局 load/store 各有 524,288 个请求，v1 均为 2,097,152 sectors，即 **4
sectors/request**。相比 v0 的 store 32 sectors/request，shared tile 已完全解决
非合并全局写。

## 6. 新瓶颈：shared-memory bank conflict

ncu 对 524,288 个 shared load 请求给出：

- 平均 **32.5-way bank conflict**；
- 163,344,423 次 bank conflict；
- shared load 的 17,040,797 个 wavefront 中 95.85% 与冲突有关；
- 全 kernel 有 16,625,928 个 excessive wavefront，占 17,301,504 的 94%；
- 工具估计消除该访问问题可带来约 93% 的局部收益空间。

这与 `tile[32][32]` 的地址映射完全吻合：同一 warp 在写出阶段按第一维变化，
相邻线程地址间隔 32 个 float，全部映射到同一 bank。

## 7. 下一步

v2 只做一个改动：shared tile 从 `[32][32]` 改为 `[32][33]`。额外一列改变
每行起始 bank，使转置读取时相邻线程落到不同 bank；全局访问、block 形状、
循环次数和边界逻辑全部保持不变，以单独量化 bank-conflict padding 的收益。
