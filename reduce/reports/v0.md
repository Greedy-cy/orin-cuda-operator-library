# Reduce v0：每线程一次全局 atomicAdd

## 1. 实验目的

建立一个正确、容易理解、但有明确性能缺陷的 Reduce Sum baseline。每个线程
先通过 grid-stride loop 计算局部和，然后对同一个全局输出地址执行一次
`atomicAdd`。该版本用于验证全局 atomic 竞争在 Orin 上的表现，并为 v1 的
block reduction 提供对照。

| GPU | Orin，8 SM，Compute Capability 8.7 |
| Jetson Linux | R36.4.7 |
| CUDA / nvcc | 12.6 / 12.6.68 |
| Nsight Systems | 2024.5.4 |
| Nsight Compute | 2024.3.1 |
| 功耗模式 | MAXN_SUPER |
| GPU 时钟 | 锁定 1020 MHz |
| EMC 时钟 | 锁定 3199 MHz |
| 编译选项 | `-O3 -lineinfo -std=c++17 -arch=sm_87` |

第一次未锁频采样时，ncu 记录的 GPU 频率只有约 306 MHz。该组结果被废弃，
以下所有正式数据均在重新锁频后采集。

## 3. 实现

```cpp
for (size_t i = index; i < n; i += blockDim.x * gridDim.x) {
  thread_sum += input[i];
}
if (index < n) {
  atomicAdd(output, thread_sum);
}
```

主尺寸使用 64 blocks × 256 threads，共有 16,384 个线程竞争同一个地址。
输入只在 benchmark 前复制一次，CUDA Event 只覆盖 reduction kernel，不包含
host/device 拷贝和输出清零。

## 4. 正确性与性能

固定随机种子 `20260809`，CPU 端使用 double accumulation 后转换为 float。

| N | GPU 结果 | 绝对误差 | Median | 有效带宽 | 正确性 |
|---:|---:|---:|---:|---:|---|
| 32 | -0.632587 | 0.000000 | 0.008016 ms | 0.015968 GB/s | PASS |
| 1,000 | 4.123612 | 0.000003 | 0.011024 ms | 0.362845 GB/s | PASS |
| 1,024 | 3.802071 | 0.000002 | 0.011200 ms | 0.365714 GB/s | PASS |
| 4,096 | 10.002267 | 0.000026 | 0.020400 ms | 0.803137 GB/s | PASS |
| 1,048,576 | -269.494141 | 0.000854 | 0.145088 ms | 28.908689 GB/s | PASS |
| 16,777,216 | 734.719543 | 0.002502 | **1.504416 ms** | **44.607917 GB/s** | PASS |

小尺寸主要受约 8–20 us 的 kernel launch/调度成本影响。主尺寸带宽只有此前
硬件画像中约 100 GB/s DRAM 读带宽的 44.6%。

## 5. Nsight Systems

命令：

```bash
nsys profile --trace=cuda,nvtx,osrt --sample=none \
  --output=profile/reduce_v0_nsys --force-overwrite=true \
  ./build/reduce_v0 --n=16777216 --warmup=1 --repeat=1
```

报告中三个 kernel 实例的 median 为 **1.493120 ms**，与独立 CUDA Event
benchmark 的 1.504416 ms 一致。时间线中没有 H2D/D2H 被计入 kernel 计时，
因此当前问题位于 kernel 内部。

## 6. Nsight Compute

采集对象为一次 `reduce_atomic_kernel`：

| 指标 | 数值 |
|---|---:|
| Kernel duration | 2.12 ms（profiling replay 开销下） |
| SM frequency | 1.02 GHz |
| Memory throughput | 30.53% |
| Compute throughput | 9.66% |
| L2 hit rate | 0.78% |
| Issue slots busy | 11.05% |
| No eligible warp | 90.27% |
| Active warps / scheduler | 7.99 |
| Eligible warps / scheduler | 0.10 |
| Warp cycles / issued instruction | 82.12 cycles |
| L1TEX scoreboard stall | 75.5 cycles，占发射间隔 91.9% |
| Theoretical occupancy | 100% |
| Achieved occupancy | 75.61% |
| Registers / thread | 16 |

虽然存在足够多的 active warps，但绝大多数周期没有 eligible warp。ncu 将
91.9% 的发射间隔归因于 L1TEX scoreboard 等待；结合所有线程在循环结束后
访问同一个 atomic 地址，可以判断瓶颈是原子读改写的依赖和竞争，而不是计算
吞吐、寄存器或 shared memory 容量。

## 7. 结论与下一步

v0 达到了作为 baseline 的目的：结果正确，但主尺寸只达到 44.61 GB/s，SM
和内存吞吐均未充分利用。v1 将在每个 block 内用 shared-memory tree reduction，
每个 block 只执行一次全局 atomic。主假设是：把 atomic 次数从最多 16,384
次降至 64 次后，eligible warp 比例和有效带宽应明显提升。
