# Softmax v4：受控寄存器缓存与最终分派

## 1. 优化假设

v2/v3 的对齐 block 路径依次读取输入求 max、再次读取输入并把
`exp(x-max)` 写入全局输出，最后读回指数值完成归一化。对
`4096×1024` 而言，ncu 已显示 L2 throughput 超过 93%，因此 v4 不再调整
规约，而是减少真实全局数据流量。

缓存只用于寄存器上界明确的形状：

- `cols<=128`：一个 warp 处理一行，每个 lane 缓存最多 4 个标量；
- `128<cols<=1024 && cols%4==0`：一个 block 处理一行，每线程最多缓存一个
  `float4`；
- 更长或非四元素对齐：保留 v3 的通用 block 路径。

缓存路径先在寄存器保留输入，完成 max 后原地计算指数，sum 规约期间仍将指数
留在寄存器，最终只写一次归一化结果。按算法最小口径，每元素只需要一次输入
读取和一次输出写入。

## 2. 正确性与尺寸分派

CPU reference 使用 double 计算。所有路径要求最大绝对误差和每行和误差均不
超过 `2e-5`，极端测试使用 `[-1000,1000]` logits。

| 1 | 32 | warp cached | 0.008608 ms | 0.008112 ms | 1.06× | 0.031558 GB/s | PASS |
| 1 | 1,024 | block cached | 0.008816 ms | 0.008672 ms | 1.02× | 0.944649 GB/s | PASS |
| 128 | 128 | warp cached | 0.009792 ms | 0.009280 ms | 1.06× | 14.124138 GB/s | PASS |
| 128 | 1,024 | block cached | 0.018064 ms | 0.015584 ms | 1.16× | 67.285423 GB/s | PASS |
| 128 | 8,192 | block general | 0.165984 ms | 0.167120 ms | 0.99× | 50.195114 GB/s | PASS |

再独立运行五轮：

| 形状 | 五轮 median（ms） | 最大跨度 |
|---|---|---:|

| `4096×128` | 0.052192 / 0.052304 / 0.052048 / 0.052128 / 0.051888 | 0.80% |

两者均低于 3% 的收口阈值。

## 4. Sanitizer：由失败定位跨阶段竞态

v4 初版在普通运行中全部通过，但 synccheck 插桩下 `17×1024` 偶发数值错误。
进一步执行 racecheck 后，工具明确报告：

```text
Read:  block_reduce_max(...): return shared[0]
Write: block_reduce_sum(...): warp leader writes shared[warp]
4 hazards, correct=FAIL
```

原因是 max 规约尾部的 block barrier 只保证 `shared[0]` 已写好；barrier 放行后，
某个 warp 可能尚未读取 max，另一个 warp 已经进入 sum 阶段覆盖相同 shared
数组。修复是在 sum 规约入口增加 `__syncthreads()`，将“所有 warp 消费 max”与
“开始覆盖 shared 数组”分隔开。相同修正回填到 v0-v3。

修复后执行：

```bash
compute-sanitizer --tool memcheck --error-exitcode=1 \
  ./build/softmax_v4 --rows=4 --cols=1003 --warmup=1 --repeat=2
compute-sanitizer --tool synccheck --error-exitcode=1 \
  ./build/softmax_v4 --rows=17 --cols=1024 --warmup=1 --repeat=2
compute-sanitizer --tool racecheck --error-exitcode=1 \
  ./build/softmax_v4 --rows=17 --cols=1024 --warmup=0 --repeat=1
```

memcheck、synccheck、racecheck 均为 0 error/hazard，结果为 PASS。这个案例说明
普通正确性运行不能代替同步分析工具。

## 5. Nsight Systems

使用 warmup 2、计时 3 次；报告包含 warmup、单次正确性 launch 和计时 launch，
因此统计 6 个 kernel 实例：

| 形状 | Kernel | nsys median |
|---|---|---:|
| `4096×1024` | `softmax_block_cached_float4_kernel` | 0.351184 ms |
| `4096×128` | `softmax_warp_cached_kernel` | 0.047952 ms |

时间线中未发现计时区间内的 H2D/D2H 传输或额外 kernel。nsys 与 CUDA Event
中值趋势一致。

## 6. Nsight Compute：主形状

| 指标 | v3 block | v4 block cached | 解释 |
|---|---:|---:|---|
| Kernel duration | 436.45 us | 411.65 us | ncu 多 pass 下仍更快 |
| Memory throughput | 93.04% | 66.75% | 实际内存事务减少，百分比下降不是退化 |
| L1/TEX throughput | 39.49% | 32.42% | 中间值不再全局往返 |
| Compute throughput | 40.87% | 37.44% | 内存与指令均减少 |
| Issue slots busy | 41.16% | 38.06% | 执行指令下降 |
| No eligible warp | 58.85% | 61.89% | 剩余依赖等待更突出 |
| Registers / thread | 32 | **24** | 编译器生成的缓存路径未增加最终寄存器数 |
| Achieved occupancy | 95.56% | 95.02% | 基本不变 |
| Executed instructions | 5,586,944 | **4,243,456** | 下降 24.0% |

有效 I/O 带宽从 78.66 提升到 94.84 GB/s，但 ncu Memory throughput 下降，二者
并不矛盾：有效带宽固定按最小输入+输出字节计算，而 v3 实际还有额外输入读取及
指数中间值读写。v4 删除这些事务后，用更低的硬件内存占用完成了更多有效工作。
当前主要建议是 L1TEX scoreboard，平均约 14.8 cycles；这是首次输入读取到后续
exp 的依赖，继续加缓存层次不能消除。

## 7. Nsight Compute：短行

| 指标 | v3 warp | v4 warp cached | 变化 |
|---|---:|---:|---:|
| Memory throughput | 84.70% | 72.92% | 实际事务减少 |
| Compute throughput | 46.01% | 46.21% | 持平 |
| No eligible warp | 51.67% | 50.07% | 略降 |
| Registers / thread | 22 | 28 | 每 lane 缓存 4 个值的代价 |
| Achieved occupancy | 82.15% | 86.40% | 未因寄存器增加而下降 |
| Executed instructions | 913,408 | **675,840** | 下降 26.0% |

短行仍以 L1TEX scoreboard 为主要 stall（约 12.2 cycles），但一次输入读取、一次
最终输出写入已经接近当前 FP32 单 kernel 数据路径的自然下限。

## 8. 结论与停止条件

- baseline 和 v4 在常规、极端、非对齐形状上正确；
- 三类 dispatch 路径均被测试，sanitizer 为 0 error/hazard；
- 关键形状五轮波动低于 1%；
- 主形状相对 v0 为 1.89×，短行相对 v0 为 6.29×；
- 最终瓶颈已从冗余全局流量转为首次读取的 scoreboard 依赖和 exp 计算；
- 更长/非对齐行未强行缓存，避免无界寄存器数组。

FP32 Softmax standalone 路线在 v4 暂时收口。FP16 输入、FP32 accumulation 将在
dtype 扩展阶段加入，不改写本轮 FP32 benchmark 口径。
