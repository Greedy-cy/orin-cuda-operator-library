# GEMM v4：同步双缓冲与预取实验

## 1. 实验假设

v3 每轮执行“global load → shared → barrier → compute → barrier”。v4 为对齐主路径
分配两份 A/B shared tile，并采用：

1. 首 tile 直接载入 shared；
2. 当前 tile 开始时，将下一 tile 的两个 `float4` 先载入线程寄存器；
3. 用当前 shared buffer 完成 16 步 FMA；
4. 全 block 完成读取后，把寄存器中的下一 tile 写入另一 shared buffer；
5. 同步后交换 read/write buffer。

这不是 `cp.async`：global load 仍经过通用寄存器，软件只能通过独立指令和 warp
调度争取部分延迟隐藏。v4 的目的正是测量这种同步双缓冲是否值得保留。

非对齐形状继续使用 v3 等价的标量 fallback。tile、线程数、每线程输出与 float4
写回均不变，因此主路径差异集中在预取时序和第二份 shared buffer。

## 2. 环境与口径

| 项目 | 值 |
|---|---|
| GPU | Jetson Orin Nano Super，8 SM，sm_87 |
| CUDA / cuBLAS | 12.6 / 12.6，cuBLAS pedantic FP32 |
| 锁频 | MAXN_SUPER，GPU 1020 MHz，EMC 3199 MHz |
| 编译 | `-O3 -lineinfo -std=c++17 -arch=sm_87 -lcublas` |
| 常规计时 | warmup 5，运行 15 次取 median |
| 长复验 | warmup 10，运行 30 次取 median |
| 正确性 | cuBLAS reference；逐元素 `atol=1e-3, rtol=1e-3` |

ptxas 报告主 kernel 使用 63 registers/thread、16,384 bytes shared memory，
`0 bytes spill stores/loads`。标量 fallback 为 64 registers、8,192 bytes shared。

三组大方阵都只比 v3 快约 2%，趋势一致但低于预设 3% 显著收益线。4096³ 的
长复验进一步得到：

| 版本 | warmup / repeat | Median | 性能 |
|---|---:|---:|---:|
| v3 | 10 / 30 | 137.918457 ms | 996.523 GFLOP/s |
| v4 | 10 / 30 | 135.245178 ms | 1,016.221 GFLOP/s |

长复验仍为 1.98% 提升，说明这是可复现的小收益，而不是一次偶然最快值；但它
仍不足以单独证明同步双缓冲具有强泛化价值。

所有形状 `violations=0`；4096³ 最大绝对误差 `2.3e-5`。

## 5. Sanitizer

| 检查 | 形状 | 结果 |
|---|---|---|
| double-buffer memcheck | `128×128×128` | `ERROR SUMMARY: 0 errors`，PASS |
| double-buffer racecheck | `128×128×128` | `0 hazards displayed`，PASS |
| double-buffer synccheck | `128×128×128` | `ERROR SUMMARY: 0 errors`，PASS |
| fallback memcheck | `37×65×1003` | `ERROR SUMMARY: 0 errors`，PASS |

双缓冲的检查重点是 buffer 翻转前的读完成同步、下一 buffer 写完后的可见性，以及
末 tile 不再执行无意义的 buffer 覆盖。

## 7. Nsight Compute：为何只有小收益

1024³ 稳态 kernel：

| 指标 | v3 | v4 | 变化/解释 |
|---|---:|---:|---|
| Duration | 2.20 ms | 2.15 ms | -2.3% |
| Roofline FP32 peak | 47% | 48% | +1 pp |
| Memory throughput | 86.28% | 88.16% | +1.88 pp |
| Compute throughput | 57.64% | 61.99% | +4.35 pp |
| Issue slots busy | 57.73% | 62.18% | +4.45 pp |
| No eligible warp | 42.26% | 37.80% | -4.46 pp |
| Executed instructions | 41,025,536 | 43,223,040 | **+5.4%** |
| Registers / thread | 64 | 63 | 基本不变，无 spill |
| Static shared / block | 8.19 KiB | 16.38 KiB | 2× |
| Achieved occupancy | 64.23% | 64.62% | 基本不变；仍由寄存器限制 |

预取确实让 eligible warp 和 issue slot 指标改善，但需要额外 buffer 翻转、条件和
shared 写入，执行指令反而增加 5.4%。第二份 shared tile 没有降低 occupancy，
因为 63 registers/thread 仍先把每 SM 限制在 4 blocks。两种效应抵消后只留下约
2% 的净收益。

因此 v4 不是失败版本，但也没有跨过 3% 的强收益线。它为 v5 提供对照：如果
`cp.async` 能绕过通用寄存器并更自然地形成流水，才可能进一步扩大收益。

## 8. 下一步

v5 使用 Ampere `cp.async` 完成 16-byte global-to-shared 搬运，并以 commit/wait
控制两级 shared buffer。保持 `64×64×16`、`4×4` 累加器和 float4 写回不变。
新增异步同步语义后再次运行 memcheck、racecheck 和 synccheck；若性能仍不足 3%，
则把重点转到 v6 的 BM/BN/BK/TM/TN 配置扫描，而不继续堆叠流水复杂度。
