# GEMM v7：一 warp 一 tile 的 FP16 WMMA baseline

## 1. 新的数据类型口径

v7 不延续 FP32 v0–v6 的 cuBLAS 比例，而是重新建立 Tensor Core 路线：

```text
A/B input:       FP16
WMMA accumulator: FP32
C output:         FP32
reference:        cublasGemmEx, FP16 input / FP32 compute / FP32 output
```

cuBLAS 使用 `CUBLAS_COMPUTE_32F` 和 `CUBLAS_GEMM_DEFAULT_TENSOR_OP`。正确性阈值
按计划从 `atol=2e-2, rtol=2e-2` 起步；实际绝对误差远低于该阈值。

## 2. baseline 映射

- WMMA shape 为 `16×16×16`；
- 一个 warp 负责一个 `16×16` C tile；
- 一个 256-thread block 包含 8 个彼此独立的 warps；
- 每个 warp 在 K 循环中直接从 global memory 加载自己的 A/B fragment；
- 没有 shared memory、跨 warp 复用、双缓冲或 cp.async；
- M/N/K 均为 16 的倍数时走 WMMA，其余形状走 FP16 输入、FP32 累加的标量
  fallback。

该版本有意只证明 WMMA API、布局、精度和 Tensor Core 指令链正确，不把“用了
Tensor Core”误当成“自然高性能”。

## 6. Sanitizer

WMMA 路径 `64×80×96` 与 scalar fallback `37×65×1003` 均通过 memcheck：

```text
ERROR SUMMARY: 0 errors
correct=PASS
```

v7 不使用 shared memory 或显式同步，因此 racecheck/synccheck 没有新增同步语义可
审计；v8 引入 block tiling 后再完整运行三类工具。

## 8. Nsight Compute：Tensor Core 为什么闲着

1024³ 稳态 WMMA kernel：

| 指标 | 数值 |
|---|---:|
| Duration | 2.26 ms |
| Memory throughput | 98.21% |
| L1/TEX throughput | 99.76% |
| Compute throughput | 17.32% |
| Issue slots busy | 11.56% |
| No eligible warp | 88.43% |
| Long scoreboard | 93.9 cycles，约占 92.8% |
| Registers / thread | 40 |
| Achieved occupancy | 97.56% |
| Executed instructions | 8,339,456 |
| Global excessive sectors | 8,388,608，占总 sector 约 50% |

occupancy 接近 100%，但每调度器平均只有 0.15 个 eligible warp，证明瓶颈不是
驻留 warp 数。每个 warp 独立加载 A/B fragment，同一个 A tile 被不同 N tiles
重复读取、同一个 B tile被不同 M tiles 重复读取；NCU 还显示每 32-byte sector
平均只利用 16 bytes。结果是 L1/TEX 饱和、long scoreboard 占绝大多数间隔，而
Tensor Core compute throughput 只有 17.32%。

## 9. 下一步

v8 用一个 block 协作加载更大的 A/B tile 到 shared memory，让多个 WMMA warps
复用数据；在寄存器中保留多个 accumulator fragments，并用两级 shared buffer
与 cp.async 形成流水。目标是同时降低 global sectors 和 long scoreboard，而不
只增加 warp 数。非对齐 scalar fallback 继续保留。
