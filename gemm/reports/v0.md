# GEMM v0：每线程一个输出的 FP32 baseline

## 1. 实现

输入和输出均为行主序 FP32：

```text
A: [M,K], B: [K,N], C: [M,N]
C[row,col] = sum(A[row,inner] * B[inner,col])
```

v0 使用 `16×16` block，每个线程负责一个输出元素，并在 K 维执行完整串行
`fmaf` 循环。相邻线程读取 B 的相邻列，因此 B 方向可合并；同一 warp 中多个线程
重复读取相同 A 元素，但 kernel 没有显式 tile 或 shared-memory 复用。

参考结果通过行主序转置等价关系调用 cuBLAS SGEMM。cuBLAS 设置为
`CUBLAS_PEDANTIC_MATH`，避免 TF32 改变 FP32 baseline 的比较口径。小尺寸和大尺寸
都用同一参考路径；误差判定为：

```text
abs(custom-reference) <= 1e-3 + 1e-3 * abs(reference)
```

`max_rel_error` 会在参考值接近 0 时被放大，因此 PASS 以逐元素混合阈值和
`violations=0` 为准。

| 4,096 | 4,096 | 4,096 | **805.372253 ms** | **170.653 GFLOP/s** | **101.475647 ms** | **1,354.403 GFLOP/s** | **12.60%** | PASS |

非对齐尺寸最大绝对误差为 `2e-6`，方阵 4096³ 最大绝对误差为 `2.3e-5`；
所有形状均为 `violations=0`。1024³ 起 custom 性能稳定在 168–171 GFLOP/s，
说明大矩阵已进入同一稳态瓶颈，而非 launch overhead 主导。

小型非对齐形状上的 88% cuBLAS 占比不能代表高吞吐能力：此时两条路径都由固定
开销主导，所以主结果只采用大尺寸。

## 4. LLM skinny-M 形状

固定 `K=N=4096`：

| M | Custom median | Custom | cuBLAS median | cuBLAS | cuBLAS 占比 | 结果 |
|---:|---:|---:|---:|---:|---:|---|
| 1 | 1.906112 ms | 17.604 GFLOP/s | 0.728576 ms | 46.055 GFLOP/s | 38.22% | PASS |
| 16 | 3.293440 ms | 163.012 GFLOP/s | 1.398112 ms | 383.997 GFLOP/s | 42.45% | PASS |
| 128 | 25.336609 ms | 169.516 GFLOP/s | 3.861824 ms | 1,112.160 GFLOP/s | 15.24% | PASS |
| 512 | 100.828484 ms | 170.387 GFLOP/s | 12.722240 ms | 1,350.381 GFLOP/s | 12.62% | PASS |
| 1,024 | 201.478745 ms | 170.538 GFLOP/s | 25.397633 ms | 1,352.872 GFLOP/s | 12.61% | PASS |

`M=1` 只有一行，二维 `16×16` block 中 15/16 的 y 方向线程越界退出，且只有
256 个有效输出线程，GPU 并行度和线程利用率都不足。v1 的通用方阵 tile 不一定
解决 GEMV 型瓶颈，后续会将 skinny-M 单独保留为调度/专用 kernel 的证据。

## 5. Sanitizer

在 `M=37, N=65, K=1003` 上执行：

```bash
compute-sanitizer --tool memcheck ./build/gemm_v0 \
  --m=37 --n=65 --k=1003 --warmup=1 --repeat=1
```

结果为 `ERROR SUMMARY: 0 errors`，数值验证 PASS。二维 grid 的 row/col 边界判断
覆盖了 M、N 的非对齐尾部，K 维为标量循环，不要求 tile 对齐。

## 6. Nsight Systems

在 1024³、warmup 2、repeat 3 下采集；报告中 custom 与 cuBLAS 各出现 6 次，
包括正确性运行、warmup 和正式计时。

| Kernel | 实例 | Median | GPU kernel 时间占比 |
|---|---:|---:|---:|
| `sgemm_naive_kernel` | 6 | 12.808400 ms | 88.7% |
| `ampere_sgemm_128x64_nn` | 6 | 1.634352 ms | 11.3% |

CUDA Event 与 nsys 的 kernel 中值一致。v0 是单 kernel，没有不必要的中间拷贝或
多 kernel 同步；差距来自 kernel 本身的数据复用和指令组织。

## 7. Nsight Compute

1024³ 的一次稳态 `sgemm_naive_kernel`：

| 指标 | 数值 |
|---|---:|
| Duration | 12.97 ms |
| Memory throughput | 95.86% |
| L1/TEX throughput | 96.00% |
| L2 throughput | 31.83% |
| Compute throughput | 63.86% |
| L1/TEX hit rate | 90.72% |
| Issue slots busy | 44.42% |
| No eligible warp | 55.58% |
| Long scoreboard | 16.0 cycles/issued instruction，约占 59.7% |
| Registers / thread | 40 |
| Achieved occupancy | 99.50% |
| Executed instructions | 186,712,064 |

NCU 还指出 global load 的一个 32-byte sector 平均只利用 18 bytes，并估算优化
该访问模式可带来约 41.9% 的局部收益。虽然 occupancy 已达 99.5%，调度器仍有
55.6% 周期没有 eligible warp；原因不是缺少驻留 warp，而是 warp 大量等待
L1TEX/global load scoreboard。

因此 v0 的核心问题是：每个输出线程都独立执行 K 循环，A/B 数据没有在 block
层面显式复用，内存管线和 L1/TEX 已接近饱和，但仅获得 cuBLAS 约 12.6% 的计算
吞吐。继续提高 occupancy 没有依据。

## 8. 下一步

v1 采用 shared-memory tiling：每个 `16×16` block 分批协作加载 A、B tile，
每个 tile 在 block 内复用后再进入下一个 K 分块。该版本保持“每线程一个输出”和
相同 block 形状，单独测量数据复用的收益；不同时加入寄存器分块、`float4` 或
双缓冲。
