# GEMM v2：64×64×16 tile 与每线程 4×4 寄存器分块

## 1. 单一优化方向

v2 将 v1 的“一线程一输出”改为 thread coarsening：

```text
block tile:   BM=64, BN=64, BK=16
threads:      256
thread tile:  TM=4, TN=4
accumulators: 16 FP32 / thread
shared:       A[64,16] + B[16,64] = 8 KiB / block
```

每轮 K tile 由 256 个线程分别协作加载 A、B 各 1,024 个元素。每线程将 4 个 A
fragment 与 4 个 B fragment 做外积，维护 16 个输出累加器。相对 v1，每轮 tile
同步和 shared 数据产生更多 FMA，降低加载、地址计算和 barrier 的摊销。

本版仍采用标量同步加载和标量写回，不加入 `float4`、双缓冲或 `cp.async`。
M/N/K 尾部使用补零与标量边界写回。

## 2. 环境与口径

| 项目 | 值 |
|---|---|

| CUDA / cuBLAS | 12.6 / 12.6，cuBLAS pedantic FP32 |
| 锁频 | MAXN_SUPER，GPU 1020 MHz，EMC 3199 MHz |
| 编译 | `-O3 -lineinfo -std=c++17 -arch=sm_87 -lcublas` |
| 计时 | warmup 5，运行 15 次取 median |
| 正确性 | cuBLAS reference；逐元素 `atol=1e-3, rtol=1e-3` |

运算量为 `2*M*N*K`；自定义和 cuBLAS 分别 warmup、分别用 CUDA Event 计时，
不包含内存分配、传输及验证。

| M | N | K | v2 median | v2 | 相对 v1 | 相对 v0 | cuBLAS 占比 | 结果 |
|---:|---:|---:|---:|---:|---:|---:|---:|---|
| 37 | 65 | 1,003 | 0.143232 ms | 33.683 GFLOP/s | 0.33× | 0.41× | 35.57% | PASS |
| 1,024 | 1,024 | 1,024 | 2.974784 ms | 721.896 GFLOP/s | 2.93× | 4.30× | 55.28% | PASS |
| 2,048 | 2,048 | 2,048 | 23.370209 ms | 735.118 GFLOP/s | 3.01× | 4.32× | 54.82% | PASS |
| 4,096 | 4,096 | 4,096 | **185.263458 ms** | **741.857 GFLOP/s** | **3.04×** | **4.35×** | **54.74%** | PASS |

大矩阵收益稳定并随尺寸略升，4096³ 相对 v1 缩短 67.1%。非对齐小矩阵则因
`64×64` tile 只有两个 block、且大量输出越界而明显退化；它证明大 tile 必须配合
shape dispatch，不能作为所有形状的默认答案。

非对齐形状最大绝对误差 `2e-6`，4096³ 为 `2.3e-5`；全部
`violations=0`。

## 4. LLM skinny-M 形状

固定 `K=N=4096`：

| M | v2 median | v2 | 相对 v1 | cuBLAS 占比 | 结果 |
|---:|---:|---:|---:|---:|---|
| 1 | 2.941536 ms | 11.407 GFLOP/s | 0.76× | 24.74% | PASS |
| 16 | 3.097824 ms | 173.306 GFLOP/s | 0.75× | 41.29% | PASS |
| 128 | 6.072800 ms | 707.247 GFLOP/s | 2.92× | **63.56%** | PASS |
| 512 | 23.417313 ms | 733.640 GFLOP/s | 3.01× | 54.29% | PASS |
| 1,024 | 46.525631 ms | 738.512 GFLOP/s | 3.03× | 54.58% | PASS |

`M<64` 时整个 tile 中多数行无效，却仍执行完整加载和计算，因此 v2 在 M=1/16
上慢于 v1；M=128 已有两个完整 M tiles，性能升到 707 GFLOP/s。后续最终
dispatcher 至少需要 small-M 与 regular-M 两类路径。

| memcheck | `ERROR SUMMARY: 0 errors` |
| racecheck | `0 hazards displayed (0 errors, 0 warnings)` |

三类工具均同时得到 `correct=PASS`。它们覆盖了二维尾块、K 尾部补零、两组 shared

## 7. Nsight Compute：从等待转向计算与资源权衡

1024³ 稳态 kernel：

| 指标 | v1 | v2 | 变化/解释 |
|---|---:|---:|---|
| Duration | 8.74 ms | 2.99 ms | -65.8% |
| Memory throughput | 91.45% | 66.75% | 内存压力显著下降 |
| Compute throughput | 71.09% | 64.17% | SOL 百分比口径受不同管线制约；roofline FP32 达峰值 35% |
| Issue slots busy | 49.23% | 64.41% | +15.18 pp |
| No eligible warp | 50.75% | 35.79% | -14.96 pp |
| Warp cycles / instruction | 24.23 | 12.03 | -50.4% |
| Executed instructions | 139,526,144 | 61,728,768 | -55.8% |
| Registers / thread | 37 | 64 | 16 个累加器的资源代价 |
| Static shared / block | 2.05 KiB | 8.19 KiB | 更大 tile |
| Achieved occupancy | 99.40% | 64.53% | 寄存器限制，理论 66.67% |

尽管 occupancy 从 99.4% 降至 64.5%，性能仍提升近 3 倍，说明“更高 occupancy
必然更快”不成立：寄存器分块减少一半以上执行指令、提高 issue slot 利用率，收益
远大于驻留 warp 减少的代价。

NCU 的下一条具体证据是写回：global store 每个 32-byte sector 平均只利用
8 bytes，产生 393,216 个 excessive sectors，占总 sector 的 8%，估算局部改善
上限约 8%。原因是每个线程用四条标量指令写连续 4 列，而同一 warp 在单条写指令
中跨线程地址步长为 4 个 float。

## 8. 下一步

v3 对 `M/N/K` 满足对齐条件的主路径使用 `float4` 协作加载与 `float4` 写回，使
每个线程的四个相邻输出合并为一次 16-byte store，并减少 load/store 指令。
非对齐尺寸保留 v2 的标量补零路径，避免为了向量化牺牲边界覆盖。v3 不改变 tile、
寄存器分块或同步结构，直接检验 NCU 指出的 sector 利用率问题。
