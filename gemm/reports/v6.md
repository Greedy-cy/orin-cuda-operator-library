# GEMM v6：有限配置扫描、small-M 路径与 FP32 收口

## 1. 扫描范围与选择原则

v6 将 v5 的 cp.async 双缓冲主体模板化，但只扫描由已有证据支持的候选：

- BM/BN 非对称配置：比较沿 M 或 N 扩大复用的差异；
- `8×4`、`4×8`、`8×8` thread tile：比较寄存器复用与 occupancy；
- 一个 BK=32 候选：检查更深 K tile 是否值得额外 shared/寄存器；
- 一个较小 BM 候选：检查更多 block 是否有利于中等 M；
- M=1 和 M=16 各一个专用映射，解决 v2–v5 一直记录的无效行计算。

所有 regular 候选固定 256 线程和两级 cp.async buffer。筛选不是自动穷举：先在
`M=512, N=K=4096` 短测，再在 M=128/1024 交叉验证；最终胜者才执行完整矩阵、
sanitizer、nsys/ncu 和稳定性测试。

`--config=0..7` 可强制复现实验；不指定时使用最终 dispatcher。

## 2. 候选资源与 M=512 初筛

短测为 warmup 3、repeat 7，性能取 median：

| ID | BM×BN×BK | TM×TN | Registers | Shared | Spill | M=512 GFLOP/s | 结论 |
|---:|---|---|---:|---:|---:|---:|---|
| 0 | 64×64×16 | 4×4 | 65 | 16 KiB | 0 | 994.292 | v5 同形状的模板化对照 |
| 1 | 64×128×16 | 4×8 | 105 | 24 KiB | 0 | 842.850 | 扩 N 与高寄存器使性能下降 |
| 2 | **128×64×16** | **8×4** | **107** | **24 KiB** | **0** | **1,185.742** | 最优 |
| 3 | 128×128×16 | 8×8 | 151 | 32 KiB | 0 | 1,145.075 | 64 累加器代价过高 |
| 4 | 64×128×32 | 4×8 | 80 | 48 KiB | 4 B load/store | 880.568 | BK=32 出现 spill，否决 |
| 5 | 32×128×16 | 2×8 | 71 | 20 KiB | 0 | 464.418 | block 更多但每 tile 复用不足 |

ID 0 因通用模板生成 65 registers，高于手写 v5 的 60 registers，因此不是完全零
开销的 v5 复刻；它用于同一 v6 二进制内部的配置对照。最终 ID 2 仍比原始 v5
的 1,073.746 GFLOP/s（同 M=512）快 10.4%。

## 3. 跨形状复筛

固定 `N=K=4096`，短测 GFLOP/s：

| Config | M=128 | M=512 | M=1,024 | 三形状判断 |
|---:|---:|---:|---:|---|
| 0: 64×64 / 4×4 | 982.560 | 994.292 | 996.332 | 稳定但低于 v5 手写版 |
| 1: 64×128 / 4×8 | 837.448 | 842.850 | 844.631 | 全面负优化 |
| 2: 128×64 / 8×4 | **1,173.673** | **1,185.742** | **1,188.343** | 三形状第一 |
| 3: 128×128 / 8×8 | 1,138.799 | 1,145.075 | 1,147.842 | 第二，但 151 registers |
| 4: 64×128×32 / 4×8 | 871.793 | 880.568 | 882.031 | spill 且慢 |
| 5: 32×128 / 2×8 | 461.758 | 464.418 | 464.917 | 数据复用不足 |

ID 2 在三个 M 上均领先，避免了“只对一个方阵调参”的选择偏差。扩大 M tile 比
扩大 N tile 更适合本实现的 shared 访问和寄存器映射；ID 3 的更高复用无法抵消
151 registers 带来的资源压力。

## 4. small-M 专用配置

| M | 自动配置 | Median | Custom | v5 同形状 | 相对 v5 | cuBLAS | cuBLAS 占比 | 结果 |
|---:|---|---:|---:|---:|---:|---:|---:|---|
| 1 | ID 7：1×256×16 / 1×1 | **0.672704 ms** | **49.880 GFLOP/s** | 11.409 | **4.37×** | 45.932 | **108.60%** | PASS |
| 16 | ID 6：16×128×16 / 1×8 | **2.275968 ms** | **235.887 GFLOP/s** | 173.490 | **1.36×** | 407.273 | **57.92%** | PASS |

M=1 配置让一个 block 只计算一行、256 列，消除了 regular kernel 的 63/64 无效
行；在本次 pedantic SGEMM 对照下略快于 cuBLAS。M=16 配置让一个 block 正好覆盖
16 行，并在这些行间复用 B tile。M=16 仍明显落后 cuBLAS，说明后续还有专用
small-M 优化空间，但 v6 已解决此前的主要映射浪费。

自动 dispatcher 固化为：

```text
M == 1   -> ID 7: BM=1,  BN=256, BK=16, TM=1, TN=1
M <= 16  -> ID 6: BM=16, BN=128, BK=16, TM=1, TN=8
otherwise-> ID 2: BM=128,BN=64,  BK=16, TM=8, TN=4
unaligned -> 64×64×16 scalar fallback
```

## 6. 稳定性

对 4096³ 独立启动进程 5 次，每次 warmup 5、repeat 15：

```text
115.422852, 115.423843, 115.437508, 115.464897, 115.455711 ms
```

最大值与最小值跨度仅 **0.036%**，远低于 3% 稳定性要求。报告主表使用首次正式
测量的 115.417854 ms，不从五次结果中挑最快值。

## 7. Sanitizer

四条实际路径均通过 memcheck：ID 7 `1×256×128`、ID 6 `16×128×128`、ID 2
`128×128×128` 和 fallback `37×65×1003` 均为 `ERROR SUMMARY: 0 errors`。

三条 cp.async 模板实例又分别通过 racecheck 与 synccheck：全部为
`0 hazards displayed` / `ERROR SUMMARY: 0 errors`，且数值 PASS。这验证了不同
BM/BN/TM/TN 实例中的异步组等待、shared 双 buffer 和输出映射。

## 9. Nsight Compute：为何低 occupancy 仍更快

1024³ 稳态 ID 2：

| 指标 | v5 | v6 ID 2 | 变化/解释 |
|---|---:|---:|---|
| Duration | 2.02 ms | 1.84 ms | -8.9% |
| Roofline FP32 peak | 51% | 56% | +5 pp |
| Memory throughput | 80.97% | 60.45% | 更大的 M tile 增加复用 |
| Compute throughput | 65.89% | 71.44% | +5.55 pp |
| Issue slots busy | 65.97% | 71.56% | +5.59 pp |
| No eligible warp | 34.01% | 28.39% | -5.62 pp |
| Warp cycles / instruction | 11.76 | 5.47 | -53.5% |
| Executed instructions | 43,096,064 | 42,615,808 | -1.1% |
| Registers / thread | 60 | 107 | 8×4 累加器代价 |
| Static shared / block | 16.38 KiB | 24.58 KiB | 更大 A tile |
| Achieved occupancy | 64.69% | **32.63%** | 寄存器限制为 2 blocks/SM |

occupancy 减半但调度效率反而提高：每 warp 的指令间隔从 11.76 降到 5.47 cycles，
memory throughput 显著下降而 compute/issue 上升。说明更多寄存器换来的 A/B 复用
与独立累加器足以覆盖延迟，单纯追求 occupancy 会选错 ID 0/5。

最终 NCU 仍报告 shared access excessive wavefront，估算局部改善空间约 5.4%；
同时 107 registers 已是明显资源约束。继续叠加同类优化很可能进入收益递减，FP32
在完成 v0→v6 的证据链后收口。

## 10. 结论与下一步

FP32 路线同时满足 baseline/final 正确、非对齐覆盖、低波动、明确最终瓶颈和
完整版本报告。最终简历可使用的当前数字是：4096³ 1.191 TFLOP/s、相对 v0
6.98×、cuBLAS FP32 pedantic 的 87.86%；必须同时标注设备和数据类型。

下一版 v7 是独立的 FP16 WMMA Tensor Core baseline，重新建立 FP16 输入、FP32
累加、FP16/FP32 输出的精度与 cuBLAS Tensor Core 对照；不会把 FP32 v6 与 FP16
cuBLAS 混在同一比例中。
